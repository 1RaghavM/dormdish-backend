# Shared deterministic meal service

`services/meal_planning.py` is a pure domain service. It performs no database/model calls or writes and enables no routes. The agent and legacy-adapter owners must use it before publishing or saving new-path proposals; the existing Gemini path remains unchanged for rollback.

## Integration contract

- `build_menu_snapshot(row, *, university, context, now, max_age)` consumes a complete trusted `menus` row, not the current `get_menu_from_supabase()` response (which returns only `menu_data`). `university` is the authenticated user's university resolved to the stored display name; `context` is the server-validated `PlanningContext` with canonical hall, university-local calendar date, and explicit meal. `now` is aware UTC. `max_age` is the server's measured freshness policy, not a client/model argument.
- The row must match university, `dining_hall`, and `date`, carry an aware `fetched_at`, and contain `menu_data.items`. Item `meal`/`meal_type` or the explicit row `meal` must establish availability. No inference from item names or unspecified meal membership. Row/item date or meal conflicts fail. Brunch is not silently treated as lunch.
- IDs are SHA-256 snapshot keys with the original item index. They include context, fetch time, and source contents, so a changed snapshot invalidates old selections. Repeated source IDs within a meal fail; duplicate food names remain distinct. Source macros support normalized `_g` names and stored Rutgers `g_` names. Items with incomplete/invalid nutrition or serving information are unavailable before the agent selects; missing macros are never estimated. An empty usable catalog fails.
- `validate_meal(snapshot, selections, *, university, context, now, restrictions=(), allergens=(), description='')` accepts only `menu_item_id` and finite servings in `(0, 20]` for each selection (1–30 items). Unknown/duplicate IDs or an invalid item reject the whole proposal. Model-supplied names/nutrition are forbidden. Re-run for the full final selection after substitutions; returned `MealProposal` nutrition and totals use trusted source values, including fractional servings, without intermediate rounding. Revalidate freshness/context at save time; retain the server-held snapshot/proposal rather than accepting client nutrition.
- Hard restrictions require matching explicit `dietary_tags`; allergens require an explicit complete `allergens` list (empty means known empty, absent means unknown). Labels are case/space/hyphen normalized. Upstream ingestion must supply verified metadata, not infer tags from names. Favorites, dislikes, and temporary tastes only affect selection/ranking and must not be passed as dietary safety evidence.
- `remaining_targets(targets: Nutrition, food_logs, completions, *, user_id, requested_date)` preserves the existing calculated/custom daily targets and subtracts owner/date-scoped evidence, clamped at zero. Food log amounts already include servings (see native `FoodLogService.addEntry`); they must not be multiplied again. Each food log has its stored `id`; its default identity is `food_log:<id>`. Completion evidence requires `completed: true`, a stable `source_id`, and consumed `totals`. Link a completion to a logged intake with the same source ID, or give genuinely separate intake a distinct ID. Equal duplicate evidence counts once; conflicting duplicate nutrition fails. Planned/uncompleted meals do not count as intake. These are internal storage records, never model arguments.

## Prerequisites and release gates

Current menu ingestion drops allergen/diet metadata and writes naive `fetched_at` values. Fix provenance at ingestion/storage before these records can be used for safety-constrained meals; do not fabricate known-empty metadata or attach an assumed timezone to historical timestamps. Source name deduplication can remove an item's availability at later meals; this service does not claim those missing items are available.

Current food-log fat/carbs may be null. Remaining-target calculation fails on incomplete nutrition instead of asserting unknown intake was zero. The caller must explain the unavailable calculation or resolve missing evidence. Current server meal-completion synchronization is absent; planned meals are not a substitute. Completion records above define the integration boundary for future authenticated persisted evidence, not a claim that completion storage exists. Client completion/intake links must be persisted before rollout can claim complete already-eaten accounting.

No legacy route, API response, dependency manifest, nutrition target formula, database schema, or feature flag is changed in this PR. Backend integration and separately reviewed independent test coverage are prerequisites to rollout. Keep rollout disabled; rollback leaves this unused pure service in place and uses existing generation routes. No live model, database, deployment, or production-data checks are part of the focused tests.
