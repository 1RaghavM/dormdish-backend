# Agent endpoint integration — rollout disabled

The six v1 endpoints use existing custom session authentication, owner-scoped `AgentStore` RPCs, and the current pass-through premium policy. `DORMDISH_AGENT_ENABLED=false`, `DORMDISH_AGENT_KILL_SWITCH=false`, and `DORMDISH_AGENT_ROLLOUT_PERCENT=0` are defaults. Admission requires enabled=true, kill=false, and membership in a stable SHA-256 user cohort; booleans are exact lowercase values and percentage is 0–100. Invalid configuration fails closed. Owner reads, run reconciliation and deletion remain available during rollback. No client flag authorizes backend access.

Request bodies are bounded to 32 KiB before decoding, then strict v1 models validate fields. Authentication, ownership, quotas and context checks happen before SSE. A request is claimed before SDK history loads; only the claim winner runs the model. Completed duplicate requests replay stored events; running duplicates return HTTP 409 with reconciliation guidance. Missing hall/date/meal produces a stored clarification without model invocation; the client must supply selected context on its next turn. No date, hall, or meal is guessed from free text.

The runtime receives the authenticated profile, bounded owner-filtered preferences, existing target calculations and canonical campus/hall selection. Known dietary labels map to hard restrictions/allergens; unknown labels fail closed. Progress and previews come from the runtime. The final event and Apply action are emitted only after `finish_turn` commits their exact event list, SDK replay and server-held payload. Disconnect cleanup closes generation and attempts bounded shielded persistence. Ambiguous writes are never repeated: a failed terminal write closes the stream for GET reconciliation; a failed confirmation response performs a read by request ID. No legacy fallback is launched. A worker that dies before cleanup leaves a leased run that storage reconciliation expires.

Apply uses only the server-stored proposal. Its payload retains untouched meals and recalculates whole-plan totals from complete finite nutrition; malformed old meal nutrition cannot be silently saved. New records omit private profile fields. Edited payloads drop the previous generation's feedback ID to avoid rating an output that has changed. The action expires no later than its source menu snapshot. Existing saved-row fingerprints prevent overwriting intervening legacy edits. Legacy hall IDs, names and slugs are matched only through the authenticated university’s checked-in registry; replacements preserve the original stored hall spelling and exact transaction guard. A different hall or ambiguous multiple rows for the selected date requires the user to resolve the existing plan instead of silently moving other meals.

`migrations/enforce_agent_daily_save_policy.sql` is a forward migration applied **after** `add_agent_persistence.sql`. It retains the existing short table lock and atomically rejects another saved row for the same owner/date, including concurrent cross-hall creation. A replacement cannot change its target's hall/date. The agent policy is deliberately stricter than inconsistent legacy policies: full nonstream generation checks any saved plan today, individual generation checks that meal/date, and full streaming/manual saving do not share those guards. Those generation routes are unchanged here. The legacy `/meal-plan/save` now verifies a supplied plan ID belongs to the authenticated owner and scopes the update itself by owner, eliminating its cross-account upsert path.

## Validation and remaining gates

Focused offline/real-PostgreSQL selfchecks cover gates and rollback reads, body bounds, duplicate clarification, terminal persistence ordering, ambiguous-write no-retry, disconnect, restrictions, preservation/math, concurrent cross-hall creation, replacement collisions and cross-owner legacy save. Run `DD_AGENT_LOCAL_PG=1 /private/tmp/dd-agent-runtime-uv/bin/python -m pytest -q -o addopts=''` against the local synthetic Docker database. No paid model or production database is involved. Dedicated independent API tests and fresh reviews remain merge dependencies.

This PR adds controlled preview/Apply, not conversational autosave, preference writes, search, meal-completion sync or legacy agent adapters. The runtime still explains its read-only phase capabilities, so a later shared runtime/action instruction update is needed before launch. Home/Planner currently omit meal selection; their context-selection integration is also required. Changed hard dietary restrictions between proposal and Apply need an atomic database/profile guard; a race-prone route-only precheck is deliberately not treated as sufficient. This is an explicit rollout blocker.

Depends on runtime PR #8 and additive persistence/source-normalization PRs. Deploy reviewed additive schema first, then this compatible backend, then gated iOS. Keep rollout off until the above functional gates, live model access, staging streaming, actual deployment limits, privacy checks, measured latency/cost and rollback gates pass. Disabling the runtime preserves stored meals/conversations and existing Gemini generation. No migration was applied to production and no deployment success is claimed.
