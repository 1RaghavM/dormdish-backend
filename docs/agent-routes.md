# Agent endpoint integration — rollout disabled

The six v1 endpoints use existing custom session authentication, owner-scoped `AgentStore` RPCs, and the current pass-through premium policy. `DORMDISH_AGENT_ENABLED=false`, `DORMDISH_AGENT_KILL_SWITCH=false`, and `DORMDISH_AGENT_ROLLOUT_PERCENT=0` are defaults. Admission requires enabled=true, kill=false, and membership in a stable SHA-256 user cohort; booleans are exact lowercase values and percentage is 0–100. Invalid configuration fails closed. Owner reads, run reconciliation and deletion remain available during rollback. No client flag authorizes backend access.

Request bodies are bounded to 32 KiB before decoding, then strict v1 models validate fields. Authentication, ownership, quotas and context checks happen before SSE. A request is claimed before SDK history loads; only the claim winner runs the model. Completed duplicate requests replay stored events; running duplicates return HTTP 409 with reconciliation guidance. Missing hall/date/meal produces a stored clarification without model invocation; the client must supply selected context on its next turn. No date, hall, or meal is guessed from free text.

The runtime receives a fresh owner-scoped database profile snapshot, bounded owner-filtered preferences, existing target calculations and canonical campus/hall selection. Known dietary labels map to hard restrictions/allergens; unknown labels fail closed. The stored `pescetarian` spelling maps to the canonical `pescatarian` restriction. Keto remains a hard `keto` dietary-tag requirement, not a soft preference or an invented carbohydrate threshold. Missing matching menu safety metadata prevents a preview for these diets. Progress and previews come from the runtime. The final event and Apply action are emitted only after `finish_turn` commits their exact event list, SDK replay and server-held payload. Disconnect cleanup closes generation and attempts bounded shielded persistence. Ambiguous writes are never repeated: a failed terminal write closes the stream for GET reconciliation; a failed confirmation response performs a read by request ID. No legacy fallback is launched. A worker that dies before cleanup leaves a leased run that storage reconciliation expires.

Apply uses only the server-stored proposal. Its payload retains untouched meals and recalculates whole-plan totals from complete finite nutrition; malformed old meal nutrition cannot be silently saved. New records omit private profile fields. Edited payloads drop the previous generation's feedback ID to avoid rating an output that has changed. The action expires no later than its source menu snapshot. Existing saved-row fingerprints prevent overwriting intervening legacy edits. Legacy hall IDs, names and slugs are matched only through the authenticated university’s checked-in registry; replacements preserve the original stored hall spelling and exact transaction guard. A different hall or ambiguous multiple rows for the selected date requires the user to resolve the existing plan instead of silently moving other meals.

`migrations/enforce_agent_daily_save_policy.sql` is a forward migration applied **after** `add_agent_persistence.sql`. It retains the existing short table lock and atomically rejects another saved row for the same owner/date, including concurrent cross-hall creation. A replacement cannot change its target's hall/date. The agent policy is deliberately stricter than inconsistent legacy policies: full nonstream generation checks any saved plan today, individual generation checks that meal/date, and full streaming/manual saving do not share those guards. Those generation routes are unchanged here. The legacy `/meal-plan/save` now verifies a supplied plan ID belongs to the authenticated owner and scopes the update itself by owner, eliminating its cross-account upsert path.

## Profile snapshot and atomic Apply safety

Deploy `enforce_agent_profile_safety.sql` after `enforce_agent_daily_save_policy.sql`, with rollout disabled during schema/backend transition. The new service-role-only `agent_get_profile` RPC returns a current owner snapshot and PostgreSQL's SHA-256 of its canonical JSON. The endpoint uses that exact snapshot for `FoodContext` and target calculation before model execution. `StoredAction.expected_profile_version` carries only the opaque digest into a nullable column on the server-held action; no password, token, email or full private profile is copied into actions, model context, API responses or saved meals.

The protected inputs are university, dietary preference/restrictions, age, height, weight, gender, activity level, goal/goal weight, weight-change speed, and all four custom nutrition targets. This covers the actual `agent_daily_targets` inputs. Conservative raw-value changes invalidate proposals, including equivalent label spellings; no cross-language JSON hashing or guessed normalization occurs. Derived BMR/TDEE fields are excluded because generation recalculates them, and account metadata changes do not invalidate a plan.

Both action persistence and confirmation first lock the user's row, then compares the stored digest with the current SQL snapshot before writing a previously unapplied action. The lock remains held through the saved-plan write and receipt commit, so ordinary profile `UPDATE` statements cannot slip between validation and write. Existing profile editing, current-day weight tracking, onboarding/auth registration, and admin profile updates use that users row; account deletion also takes its row lock. Auth login metadata, password, subscription/referral and calendar updates are outside the protected field set. This audit changes no legacy writer.

A profile change during generation prevents storing or emitting an Apply action. A definite `stale_profile` transaction rejection is converted into a persisted terminal error with no action and empty SDK replay; unknown database failures remain non-retryable ambiguous writes requiring reconciliation. Changes after preview cause HTTP 409 `Agent request stale_profile` at Apply, with no saved-plan write, receipt or quota charge committed. Existing pending proposals without a digest fail closed. New actions without a valid expected digest are rejected at finish. An already applied action or receipt remains idempotently recoverable after profile changes. Clients must obtain a new preview after a stale-profile conflict; they cannot supply the profile digest in the strict confirmation body.

Focused synthetic PostgreSQL checks cover changed profiles before finish/after preview, missing and legacy metadata, unaffected account fields, private-field exclusion, and applied-action recovery. Independent companion tests must additionally verify concurrent profile updates and the complete router/SDK/storage path before review. No production migration has been applied.
