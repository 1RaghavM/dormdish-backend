# Agent persistence (rollout disabled)

Apply `migrations/add_agent_persistence.sql` once, before deploying callers. The migration is additive, transactional, and uses the actual custom-session `public.users(id)` owner, not Supabase Auth. New tables have RLS enabled with no anon/authenticated policies or grants. RPCs are SECURITY INVOKER; PUBLIC/anon/authenticated execution is revoked. Only the privileged backend role may call them; each operation still requires the authenticated owner. Never expose that role key to clients or model tools.

`AgentStore(client, authenticated_user_id)` is synchronous like the existing Supabase client; async callers must dispatch database work off the event loop. It accepts authenticated context at construction. `claim_turn(conversation_id, TurnRequest)` returns `(claimed, RunState)`: only the winner runs the model. Identical duplicates return the recorded state; changed payloads or conversations conflict. `get_run(request_id)` reconciles uncertain writes without retrying generation. Infrastructure failures become the sanitized `StorageError('unavailable')`; preserve the same request ID when reconciling. Other codes: `not_found`, `conflict`, `busy`, `quota`, `expired`, `invalid`, `stale_plan`.

`finish_turn(terminal_run, SDK_to_input_list, assistant_text, StoredAction | None)` atomically records ordered events, bounded transcript/replay and an optional server-held action. `StoredAction` contains the typed `PendingAction`, the **trusted service's validated existing-format meal_plan_data**, and optional target plan ID/version. Passing wire validation alone does not ground meals; this API is not a model tool. Confirmation accepts only action ID plus `ConfirmActionRequest`, returns a complete RunState containing the canonical saved ID, and cannot substitute another meal. `get_saved_plan(id)` returns `{plan, version}`; replacement requires its opaque full-row version. Confirm checks the version under lock. Creation requires absence of any existing plan at that owner's hall/date; if one exists, the service must explicitly select a plan and prepare an authorized replacement. No silent overwrite or fuzzy matching.

Confirmation briefly takes SHARE ROW EXCLUSIVE on `saved_meal_plans` because legacy writers do not share a proven unique/version protocol. This prevents a legacy write racing the expected-absent/version check. It serializes all saved-plan writes during this short transaction; no network/model work runs under this lock. Remove it only after verifying deployed uniqueness and migrating every writer to the common concurrency protocol. This migration does not guess a unique index against unknown production duplicates.

Limits are deliberately fixed for this release: 20 live conversations per owner, 60 new turn/confirmation requests per hour, 5-minute run lease, 100 transcript messages, 512 events/512 KiB per outcome, 128 SDK history items/256 KiB, and 256 KiB per action. Quotas survive conversation deletion, and duplicates do not consume quota. An expired running outcome reconciles to a terminal, nonretryable error; late workers cannot finish it. Expiration does not imply a preference/tool side effect was undone. Review persisted state before a new request.

Replay uses only the SDK `to_input_list()` array, never a second server continuation ID or old transcript reconstruction. Oversized history resets the whole array, preserving tool-call/result pairs. The next turn loads current profile/preferences afresh. `clear_history()` increments an owner-scoped revision across conversations so in-flight runs cannot restore forgotten context; preference-forgetting integration must call it and must not rebuild history from transcript text. That future integration is outside this persistence PR.

Conversation retention is 30 days from creation (including associated messages/runs/applied-action receipts). Unapplied proposals expire within 24 hours; `agent_purge_expired()` deletes them and expired conversations. Schedule this service-only maintenance RPC daily before rollout. Reads reject expired conversations even if maintenance is late. Foreign-key cascades remove all four new tables' user-owned records when a `public.users` row is deleted. Conversation deletion cascades runs/actions but preserves already-saved meals. Emergency rollback disables callers and keeps additive tables/data.

Local evidence: `DD_AGENT_LOCAL_PG=1 /private/tmp/dd-agent-foundation-uv/bin/python -m pytest tests/test_agent_storage_unit.py -q` uses synthetic base tables in a throwaway database in the local PostgreSQL 17.11 Docker container `dd-agent-migration-db`. No production data or paid model calls. Companion independent database tests and fresh PR review are required before merge; live schema/deployment checks remain rollout gates.

Current integration boundaries: Apply confirmations are implemented; generate-and-save in the original turn still needs an authorized atomic auto-apply path (do not call confirmation while its turn is running). Preference writes/forgetting are not implemented here; a future shared preference mutation must invalidate replay atomically, not assume two unrelated network calls commit together. No routes, feature flags, dependency manifests, or existing meal-writer behavior are changed by this PR.

Implementation selfchecks cover owner/duplicate/busy boundaries, exact confirmation payload and ID, parallel claims/saves, concurrent legacy inserts, stale replacement (including unchanged legacy timestamps), expected-absent creation, late-worker rejection, expiry, failed-finish rollback, history bounds/forgetting, RLS denial, retention/account cascades, and quotas after deletion.
